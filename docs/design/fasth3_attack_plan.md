# FastH3 — Attack Plan

Addendum to `fasth3_status_handoff.md` and `fasth3_roadmap.md`. Written against
branch `fasth3-mlx-runtime` while the 33B DMD job is queued.

Intended for the `fasth3-mlx-runtime` workstream — move this file there.

## 0. The correction that reframes the plan

**M5 base is not faster than M4 Max.** It has 10 GPU cores against the M4 Max's
40; the per-core Neural Accelerators roughly close that on matmul, so treat
M5 base ≈ M4 Max. Apple's "3.8× faster" headline is M5 base vs **M4 base**, not
vs M4 Max. Our one real measurement (Wan-1.3B, 3-step, 480×832×81, int8, TAEHV
= 117.6 s denoise) was taken on an M4 Max, so it is roughly the M5-base number
too.

Scaling that by params × tokens × steps (H3 latents are ~16.6k tokens after
2×2 patchify — about half Wan's 32.7k — but the Quality grid is 6-step, which
gives it back):

| Size | denoise | +RIFE | +RIFE +3-step | +full stack |
|---|---|---|---|---|
| 33B | 50 min | 19 min | 9.3 min | 3.1 min |
| 14B | 21 min | 7.9 min | 4.0 min | **79 s** |
| 8B | 12 min | 4.5 min | 2.3 min | **45 s** |
| 5B | 7.7 min | 2.8 min | 85 s | **28 s** |

Treat as ±2×. These are arithmetic, not measurement — which is why §4 puts a
real measurement first.

### The consequence

- **Speed stack ≈ 16×** (RIFE 2.71× measured × 3-step 2× × TeaCache ~1.5× ×
  half-res+upscale ~2×).
- **Size choice 33B→8B ≈ 4.1×.**

**The stack is worth about four times more than the size decision, and almost
none of it is built.** 8B on its own is 4.5 minutes and not a product. 14B with
the stack is 79 seconds and is one. The size debate has been absorbing attention
that belongs on the stack.

Keep the **33B → 14B → 8B cascade** — 2.4× then 1.75× beats a single 4.1× hop,
and it yields three shippable checkpoints. But build the stack *in parallel*,
not after.

## 1. Two products, and they use different formats for a real reason

The "be excellent at one axis" instinct is right, and it maps cleanly onto a
hardware asymmetry we have now measured.

| | **FastH3 Quality** | **FastH3 Turbo** |
|---|---|---|
| Target | RTX 5090 / Blackwell | Apple Silicon |
| Model | 33B, later 14B | 8B, later 5B |
| Format | **NVFP4 (W4A4)** | **affine int8 (weight-only)** |
| Weights | 33B → 18.6 GB (fits 32 GB 5090) | 8B → 8.5 GB, ~4.9 GB resident with the AdaLN cache |
| What the format buys | **memory *and* speed** | **memory only** |
| Steps | 6-step Quality grid | 2–3 step |
| Post | none — native res | RIFE + upscale |

**Why different formats is correct, not inconsistent:** on Blackwell,
`nvfp4_config.py` quantizes activations too (`quantize_input()` →
`flashinfer.mm_fp4`), so the integer path actually engages and NVFP4 delivers
both memory and throughput. On Metal, `mx.quantized_matmul` dequantizes to fp16
and does fp16 arithmetic, so no weight-only format can produce speed — measured
and written up in `mac_quantization_findings.md`. Same model, different
bottleneck, different answer.

CUDA ladder at NVFP4: 33B → 18.6 GB (32 GB cards), 14B → 7.9 GB (16 GB cards),
8B → 4.5 GB (8–12 GB cards). That is the volume NVIDIA market, and it comes free
from the same pruned checkpoints.

## 2. The dataset problem, and the fix

~50k VGGSound clips with raw label captions, against FastWan's 600k Wan-Syn
corpus — 12× less data for a *harder* job, since these runs do capacity recovery
and step distillation together. Two things are wrong and they have different
fixes.

### 2a. Caption quality — fix first, it is nearly free

Raw VGGSound labels ("dog barking", "playing piano") are class labels, not
descriptions. For a text-to-video-audio model the caption distribution is a hard
ceiling on prompt adherence, and no amount of extra clips raises it.

**Qwen3-VL-32B is already loaded in the preprocessing pipeline** for text
embeddings (`scripts/fasth3/preprocess_h3_corpus.py`). Caption each clip with it
during the same pass instead of embedding the label. This is the highest
leverage change available and it costs one extra generate call per clip on a
model already resident.

Do this **before** the corpus extension finishes, so the remaining ~25k clips
get good captions on the first pass and only the existing 24.7k need a re-run.

### 2b. Volume — teacher-generated synthetic corpus

DMD2 is a *distribution-matching* objective: it needs the teacher's score
function over prompts, not real video-text pairs. That is exactly why FastWan
distills against `Wan-Syn_77x448x832_600k` — 600k **synthetic** samples
generated by the teacher.

The same move applies here, and it is strictly better than scraping more real
video:

- distribution matches the teacher exactly, which is what DMD is fitting;
- prompt coverage is controllable — you choose the distribution rather than
  inheriting VGGSound's;
- audio comes from the teacher, so AV pairing is coherent by construction;
- it scales with GPU time rather than with licensing and scraping.

Cost is real teacher inference, but it runs on the same cluster between
training jobs and is resume-safe in the same way the current preprocessor is.

**Third option, cheapest volume:** VGGSound has ~200k clips total and you are
using ~50k. Extending is preprocessing time only. Do it, but it does not fix
2a and it inherits the weak-caption problem unless 2a lands first.

**Recommended order:** captions (2a) → synthetic corpus (2b) → VGGSound
extension as filler.

## 3. Gaps still open

| Gap | Why it bites | Fix |
|---|---|---|
| **No latency measurement at any size** | The entire size decision rests on arithmetic like §0 | §4, step 1 — an afternoon |
| **No validation callback** | 4000 iterations of loss-only on a 2.4× compression; mushy joint-AV does not show in the loss | Land before the 14B run starts |
| **`audio.desync` not gated** | Native audio is the differentiator and AV sync is the specific failure of depth pruning | Add from `fastvideo/eval/metrics/audio/` |
| **EMA removed** for FSDP2 DTensor mismatch | Wan int8 **v1 failed on an EMA bug**; v2 fixed it with world-size-portable state and `decay: 0.98`. Removing EMA is a regime change, not a simplification | Fine as bring-up; do not let it become the silent default |
| **TeaCache is a dead flag** | `enable_teacache` is plumbed through the API and consumed by nothing. ~1.5–2×, model-agnostic, no kernel work | Highest-value stack item |
| **`mx.compile` and `FASTVIDEO_MLX_FAST_NORM` off by default** | Both built, both measured, both disabled | Flip them |
| **MLX runtime not end-to-end** | No sampler wiring, no BigVGAN audio decode, no ViT video decoder — so no e2e number is even possible | On the roadmap; sequence it before launch, not after |
| **Critic inits from full 33B while student is pruned** | 33B teacher + 33B critic + 14B student resident is most of the memory bill | Confirm intentional |

## 4. Sequencing — what to do now

The 33B DMD job and the corpus extension are queued. Everything below runs
around them.

**Now, no GPU needed:**

1. **Measure per-step MLX latency at 33/14/8/5 block counts on the M5.** The DiT
   core and parity are done, so time the DiT forward alone at the real token
   count — no sampler, no audio decode, no video decoder required. This replaces
   §0's arithmetic with fact and settles the size question.
2. **Patch caption generation into the preprocessor** (§2a) before the extension
   job consumes the remaining ~25k clips.
3. **Land the validation callback and the `audio.desync` gate** before the 14B
   run starts.

**In parallel with the 33B run — this is the real leverage:**

4. **Build the speed stack.** In order of value per unit effort: TeaCache
   (~1.5–2×, no kernel work), flip `mx.compile` and fast-norm on, RIFE
   forward-ported onto this branch, then the resolution ladder (generate low,
   upscale). Worth ~16× combined — four times the size decision.

**After the 33B lands:**

5. Prune to 14B, DMD, gate.
6. Prune 14B → 8B, DMD, gate. Launch on 8B (Turbo) + 33B (Quality).
7. 5B as the fast-follow probe if the latency numbers argue for it.

**Continuously:** start the synthetic corpus (§2b) whenever the cluster has idle
capacity between jobs.

## 5. Notes for the engineer running this

- **Get the latency number before the next pruning decision.** It is the missing
  input to the choice actually being made, and it is cheap.
- **The speed stack outranks the size choice by ~4×.** If effort is contested,
  TeaCache beats another pruning experiment.
- **Fix captions before extending the corpus**, or you will preprocess 25k clips
  twice.
- **Do not re-add EMA blindly** — but do not forget it either. The Wan recipe
  that works uses it; this one has it removed for an unrelated FSDP2 reason.
- **Say explicitly whether 24.7k clips is enough to start the 14B run**, or
  whether the extension to 49.9k is a hard gate. That ambiguity is currently
  blocking-or-not for the whole schedule.
- **Run the 5B pruning in parallel with 14B** — the pipeline is size-agnostic,
  it is a `--keep-blocks 8` flag, and it costs a pruning pass on GPU time you
  are already queuing.

## 6. Reconciling with the 8/16 org meeting

Notes from the FastVideo/FastGen sync. Most of it validates the plan above; three
items change it.

### Validates what we already decided

| Org item | Our §  |
|---|---|
| Target synth data split (480p / 1024×576 / 720p, 5–15 s) | §2b — synthetic corpus from the teacher |
| "~150k split dataset from fastgen" | §2b, but **theirs is 3× the corpus we were scoping**. Take it rather than duplicating. |

| "Parse and categorize the prompts and concepts" | The stratified taxonomy we recommended over a flat seed list |
| NVFP4 named in the FastVideo goal | §1 Quality product, and §3's flag that 33B needs a QAT pass |
| Step-distillation + sparse attention as the two named levers | §0 speed stack |

### Changes the plan

**1. PDD (Parallel Decoding Distillation) may replace DMD2.** NVIDIA + Weizmann,
[arXiv 2607.26004](https://arxiv.org/html/2607.26004v1),
[project page](https://research.nvidia.com/labs/genair/pdd/). Compresses to 4–8
NFE **without variational score distillation and without adversarial losses** —
so it drops the critic network entirely. Reported SOTA at 4–8 NFE on **LTX-2.3
text-to-video/audio** and **Wan 14B**, plus a reported improvement in generated
diversity. Being ported to FastVideo, "ready 1–2 weeks."

Three reasons this matters more to us than to the org generally:

- **It drops the critic.** Our 14B config holds a 33B frozen teacher + a 33B
  trainable critic + a 14B student. Removing the critic removes roughly a third
  of resident training memory at 33B scale — that is fewer GPUs per run, or
  larger batches on the same 16.
- **It is validated on joint video+audio** (LTX-2.3 T2VA), which is the modality
  our DMD2 work had no external precedent for.
- **Diversity.** DMD is known to trade diversity for step count, and mode
  collapse in a step-distilled student is exactly the failure that would not show
  up in a loss curve.

**Recommendation: do not launch the 14B or 8B DMD2 runs until PDD lands or is
explicitly rejected.** The 33B run in flight is fine — it is the pruning parent
either way. But committing two more cascade hops to DMD2 one to two weeks before
a possibly-better method arrives is the wrong bet, and the cascade is the
expensive part.

**2. VSA is a CUDA-only speedup, and it may hurt the Metal path.** Org numbers:
triton block-64 at 500–600 TFLOPS, flashinfer block-64 at 800, FA4 block-256 at
~1.4k, with work planned to bring block-64 to ~1.1–1.4k. That is a large win —
for Quality.

None of it reaches Turbo. VSA is ThunderKittens/CUTLASS on `sm_90a`/`sm_100`;
`fastvideo/platforms/mps.py` returns SDPA unconditionally. Worse, two mismatches
appear if we are not deliberate:

- **Training with 90% VSA and deploying dense on Metal** means the student is
  optimized for an attention pattern it will never run in. Deploying dense gives
  it *more* attention than trained, which is likely benign — but it is untested,
  and none of the VSA speedup transfers.
- **Generating the synthetic corpus with a VSA-sparse teacher** — the meeting
  flags "divergence or loss compared with base model" as a con. For DMD this is
  sharper than it looks: DMD fits a *distribution*, so a corpus generated by an
  approximation of the teacher trains the student to match the approximation. If
  that corpus then trains a model we deploy dense on Metal, the mismatch
  compounds twice.

**Ask before consuming the 150k corpus: was it generated dense or VSA-sparse?**

**3. Resolution target is 720p, not 480p.** Our latency table in §0 assumes 480p.
720p is ~2.25× the tokens, so every Mac number scales accordingly — 8B with the
full stack goes from ~45 s to ~100 s. Either Turbo ships at 480p base and
upscales (which is the §0 stack's plan anyway), or the Mac numbers need redoing
at the org's target. Worth stating explicitly rather than letting the two
roadmaps drift on resolution.

### Gap the meeting does not cover

**Apple Silicon appears nowhere in the notes.** The FastVideo goal names
step-distillation, sparse attention, and NVFP4 — and two of those three are
CUDA-only. If Turbo is a real product it needs to be raised in that forum, or it
will keep receiving zero infrastructure investment while Quality gets VSA
kernels and NVFP4 work.

Also worth pulling from the org side: **"testing fixing audio shift."** Our MLX
runtime hardcodes video shift 12 / audio shift 3 in the dual rectified-flow
scheduler. If that constant is being corrected upstream, the MLX runtime and its
parity test inherit the bug until it is synced.
