FastWan-MLX: 720p video generation, natively on Apple silicon

TL;DR: A five-second, 720p, text-to-video clip, generated start to finish on a Mac. Today we're introducing FastWan-MLX, a family of three open-source video models (1.3B, 5B, and 14B) built by FastVideo and Wan, trained to run natively on Apple silicon through our new MLX runtime. The 5B makes 720p video out of the box and fits in 16 GB of unified memory. The 14B is the largest video model we've ever run on a laptop. And the 1.3B is the fastest way to make a video on a Mac, period.

Apple silicon Macs are genuinely capable machines, and there are tens of millions of them. We want every one of those machines to run open-source video generation locally — no account, no queue, no meter running. FastWan-MLX is that release: FastVideo's models, Wan's architectures, and a new MLX runtime, all working together so a much wider audience gets access to local, open-source video generation.

Why a Mac release, and why now

The Mac has quietly become a serious AI machine. Tens of millions of capable GPUs with unified memory are already on people's desks. The M5 generation added dedicated Neural Accelerators, per-core matrix units that Metal FlashAttention-class kernels already exploit for up to 4.6× faster generation over M4. MLX matured into a real framework with fused kernels, graph compilation, and quantized formats, and macOS 26 / Metal 4 gives it a stable driver-level path. Local AI on Mac has gone from curiosity to default for language models. Video generation is the obvious next step, and it's the one we build. So we brought the core of FastVideo to Mac: the actual DiT, sampler, and decoder, running natively on Metal.

The MLX runtime

With FastWan-MLX, FastVideo supports Apple silicon natively through a new MLX runtime: the same models, pipeline, and training code that run on CUDA, now first-class on Metal. The design target here is MLX and unified memory, and the runtime reflects that layer by layer:

  • MLX-first DiT, dense attention. The denoising loop runs natively on the Metal GPU with mx.fast.scaled_dot_product_attention, 100% dense. The 3-step DMD sampler runs on-device too; no tensor leaves unified memory, and the whole step is one compiled MLX graph.
  • INT8 where it counts. Every DiT matrix weight is affine INT8 (group 64) via mx.quantized_matmul; norms and modulation tables stay fp16.
  • Memory choreography. The umT5 text encoder loads in bf16, encodes once, and frees before the DiT loads. Decode defaults to TAEHV (Ollin's tiny Wan autoencoder, MIT-licensed and vendored), a fraction of the full Wan VAE's cost. Peak memory is the largest single stage, not the sum, which is why a 5B fits in 16 GB and a 14B in 24.
  • Pre-quantized checkpoints + prompt cache. Packed INT8 weights, scales, and biases stored directly; reloads skip requantization, and a content-addressed prompt cache makes repeat generations start in seconds.

How we chose INT8

We evaluated the candidate low-bit formats the way we evaluate everything: by training on them and measuring. For now, we believe INT8 is the best option for Apple silicon: it is the most accurate format we measured at its memory cost, and it is the reliability sweet spot across Apple generations. The alternatives (MXFP4, NVFP4) reconstruct weights less accurately at comparable memory, and we think there is more work to be done on those paths, from our side and from the frameworks underneath them, before they're the right answer here. We'll keep evaluating.

Affine INT8 is the most accurate format we measured at its memory cost. Integer formats beat float formats at equal bit width: E4M3 spends its bits on dynamic range that per-group scaling has already made unnecessary; affine int8 spends all 8 bits on 256 uniform levels across each group's actual range.

We also took the natural next hypothesis seriously: quantizing activations as well as weights (W8A8) so the integer matrix units engage directly. We built a fused int8×int8 Metal kernel and calibrated it against real DiT workloads; it is correct to within 3×10⁻⁶ of the reference, but on today's MLX/Metal kernel surface it does not yet beat fp16 at DiT shapes. We think there is more work to be done there from both ends, the kernel and the framework API, and we'll keep at it. For this release, INT8 for memory and dense fp16 attention is the right call.

Generation modes

The runtime ships several generation modes that compose, each behind a quality gate:

  • Fast mode (RIFE): generate every Nth frame and interpolate the rest with Apple-silicon-native rife-mlx. --fast --fast-factor 2 roughly halves diffusion work; --fast-sharpen restores edge crispness.
  • Spatial fast mode: denoise at a fraction of the target resolution, then bilinear-upsample the clean latents back before decode. No second denoise, roughly scale² fewer tokens, and it composes with fast mode for fewer frames and fewer pixels.
  • Refine mode (two-pass) — generate at base resolution, then a second denoising pass with the same DiT at higher resolution. No LoRA, no super-resolution weights, no training; a meaningful quality lever that needs no new model.
  • Quality mode: full Wan VAE decode (bf16) instead of the default TAEHV, one flag away (--decode-backend wan-vae).
  • Prompt enhancement: an on-device pre-pass that expands a short prompt into Wan-style cinematic shot language, via a local mlx-lm model or a deterministic template, with an on-disk cache.
  • Draft attention (experimental): windowed attention with sinks for interactive prompt exploration, gated behind an SSIM check. Dense attention stays the default for final renders.

How to run

python examples/inference/basic/mlx_wan_prompt_to_video.py   --model-root ~/models/fastwan-mlx   --mlx-checkpoint ~/models/fastwan-mlx/mlx_dit   --prompt "A fox runs through a misty pine forest, leaves kicking up behind it."

The defaults are the release configuration. Fast mode is --fast --fast-factor 2, spatial fast mode is --fast-spatial, refine is --refine, quality mode is --decode-backend wan-vae, prompt enhancement is --enhance-prompt. The Apple Silicon guide covers fast-reload, memory tiers, and troubleshooting.

What's next

FastWan-MLX is the start of the Mac track, not the end of it. We're continuing to experiment and to improve: more model families coming to the MLX runtime, larger models at the quality end, and even faster generation at the speed end. Image-to-video and longer clips are on the roadmap, and we keep pushing the quantization and kernel work forward so each release is better than the last.

We also welcome contributions. The runtime, the recipe, and the benchmarks are all open, and there is real room to move them. And we're glad to work with the platform teams whose silicon makes all of this possible; if that's you, we'd love to talk.
