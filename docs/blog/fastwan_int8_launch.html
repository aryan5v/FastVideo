FastWan INT8 on Apple Silicon: 720p video generation, entirely on your Mac

TL;DR: A five-second, 720p, text-to-video clip, generated start to finish on a Mac. No cloud, no datacenter GPU. Three models (1.3B / 5B / 14B), one recipe, one rule we now hold after two failed attempts proved it out: on Apple silicon, quantization is a memory decision, not a speed decision. This post shows the models, the runtime, and the receipts — including the two formats that didn't make it.

A year ago, "local video generation" meant owning a $2,000 GPU. We think it should mean opening your laptop. Today we're releasing the FastWan INT8 family for Apple silicon, and the native MLX runtime that runs it. The 5B makes 720p video out of the box and fits in 16 GB of unified memory. The 14B is the largest video model we've ever run on a laptop. The 1.3B is the fastest way to make a video on a Mac, period.

Why a Mac release, and why now

FastWan-QAD proved you can co-design a model, a quantization format, and a runtime to make a 5-second video in 1.8 seconds on a single RTX 5090. That's still a datacenter card. Meanwhile, the Mac quietly became a serious AI machine: tens of millions of capable GPUs with unified memory, M5's new Neural Accelerators (per-core matrix units that Metal FlashAttention-class kernels already exploit for up to 4.6× over M4), a matured MLX with fused kernels and graph compilation, and macOS 26 / Metal 4 underneath. Local LLMs on Mac went from curiosity to default. Video generation is the obvious next step, and it's the one we build. So we brought the core of FastVideo to Mac — not a demo, not a cloud-backed shim: the actual DiT, sampler, and decoder, running natively on Metal.

The Mac inference stack

With this release, FastVideo supports Apple silicon natively through a new MLX runtime — the same models, pipeline, and training code that run on CUDA, now first-class on Metal. The co-design target here is MLX and unified memory, not tensor cores and HBM, and the stack reflects that layer by layer.

  • MLX-first DiT, dense attention. The denoising loop runs natively on the Metal GPU with mx.fast.scaled_dot_product_attention, 100% dense. The 3-step DMD sampler runs on-device too — no tensor leaves unified memory, and the whole step is one compiled MLX graph.
  • INT8 where it counts. Every DiT matrix weight is affine INT8 (group 64) via mx.quantized_matmul; norms and modulation tables stay fp16.
  • Memory choreography. The umT5 text encoder loads in bf16, encodes once, and is freed before the DiT loads. Decode defaults to TAEHV (Ollin's tiny Wan autoencoder, MIT-licensed and vendored) — a fraction of the full Wan VAE's cost, which removes it from both the latency and the memory peak. Peak memory is the largest single stage, not the sum — which is why a 5B fits in 16 GB and a 14B in 24.
  • Pre-quantized checkpoints + prompt cache. Packed INT8 weights, scales, and biases stored directly; reloads skip requantization, and a content-addressed prompt cache makes repeat generations start in seconds.

QAD, retargeted to MLX

Post-training quantization visibly damages a 3-step model — with only three denoising steps there's no room to recover from weights knocked off their trained values. So we make the model live in its deployment precision during training: the training-time fake quantizer transcribes MLX's affine quantization arithmetic (the fp32 group min/max, the negative-scale anchoring, the integer zero-point re-fit), pinned against mx.quantize/mx.dequantize by tests in the suite. The recipe is quantization-aware DMD: a frozen teacher, a critic, and a student initialized from the already-distilled FastWan checkpoint whose every forward computes on the INT8 deploy grid, gradients passing straight through to the real weights.

How we chose INT8

Two other formats were serious candidates. We evaluated both the way we evaluate everything — by training on them and measuring — and both fell short. The data is below, because the community runs these same experiments and should not have to repeat our spend.

MXFP4: ruled out on quality

Our first QAD runs used the MXFP4 grid, at both 1.3B and 14B. Neither met the bar. The 14B run consumed 26 GPU-days over 4000 steps and produced washed-out, undertrained video. The reconstruction numbers explain why: MXFP4 is the least accurate format we measured.

Affine INT8 is 12.4× more accurate than MXFP8 and 22× more accurate than MXFP4 at comparable memory. Integer formats beat float formats at equal bit width: E4M3 spends its bits on dynamic range that per-group scaling has already made useless; affine int8 spends all 8 bits on 256 uniform levels across each group's actual range.

W8A8: ruled out on speed

The obvious follow-up is to quantize activations as well as weights, keeping the matmul in the integer domain so the Neural Accelerators actually engage. Ideogram shipped that pattern on consumer GPUs. We built it and measured it for Wan on Apple silicon.

Activation calibration on GB200 (every Linear in the 5B and 14B, across the three DMD timesteps, with random and real umT5 context) told us the scheme was viable: the bulk of every layer fits int8 with per-token scales, and only ~7% of layers — almost all cross-attention to_q — are outlier spikes we would hold in fp16. Real text embeddings make those outliers worse, not better, so the keep-list is not a randn artifact. We then wrote a fused int8×int8 Metal kernel (mx.fast.metal_kernel: per-token activation scales, per-out-channel weight scales, int32 accumulate). It is bit-close to the dequantized reference (max abs error 3×10⁻⁶), and we set the ship bar in advance: ≥1.2× faster than fp16 at DiT shapes, or we don't ship it.

M5's fp16 GEMM is excellent — the bottleneck is the kernel surface, not the silicon. Today's MLX custom-kernel API gives you a scalar int8 multiply in shader code; it does not bind the Neural Accelerator integer tensor path. Until that path is public and stable (or a lower-level kernel clears the 1.2× bar), quantization on Mac is a memory lever, not a speed lever. Weight-only mx.quantized_matmul stayed near fp16 throughout — the dequant-then-fp16 behavior the survey predicted, not a hidden fast path.

The decision: INT8

Quantization on Apple silicon is a memory decision, and INT8 is the most accurate way to spend 8 bits. 5.3 GB for the 5B, 14.9 GB for the 14B — model classes that used to require a datacenter, in laptop memory. Speed comes from step count, fused kernels, and the fast modes below.

Generation modes

Temporal and spatial shortcuts compose, and every one ships behind a quality gate.

  • Fast mode (RIFE) — generate every Nth frame, interpolate the rest with Apple-silicon-native rife-mlx. --fast --fast-factor 2 roughly halves diffusion work; --fast-sharpen restores edge crispness.
  • Spatial fast mode — RIFE's spatial twin: denoise at a fraction of the target resolution, then bilinear-upsample the clean latents back before decode. No second denoise, ≈ scale² fewer tokens. Composes with --fast for fewer frames and fewer pixels. (MetalFX is deliberately not used — it wants game-engine motion vectors and depth that diffusion output doesn't have.)
  • Refine mode (two-pass) — the H3 / LTX-2 pattern, ported into the runtime: generate at base resolution, re-noise, and run a second denoising pass with the same DiT at higher resolution. No LoRA, no SR weights, no training — the biggest quality lever that doesn't need a new model.
  • Quality mode — full Wan VAE decode (bf16) instead of the default TAEHV, one flag away (--decode-backend wan-vae).
  • Prompt enhancement (Context-IR-style) — an on-device pre-pass that expands a short prompt into Wan-style cinematic shot language, via a local mlx-lm model or a deterministic template, with an on-disk cache. Wan's training captions are long and cinematic; short prompts leave quality on the table.
  • Draft attention (experimental) — windowed attention with sinks for interactive prompt exploration, gated behind an SSIM check; dense attention stays the default for final renders.

How to run

uv pip install -e '.[mlx]'
huggingface-cli download [TODO: final HF id] --local-dir ~/models/fastwan-qad

python examples/inference/basic/mlx_wan_prompt_to_video.py \
  --model-root ~/models/fastwan-qad \
  --mlx-checkpoint ~/models/fastwan-qad/mlx_dit \
  --prompt "A fox runs through a misty pine forest, leaves kicking up behind it."

The defaults are the release configuration. Fast mode is --fast --fast-factor 2, spatial fast mode is --fast-spatial, refine is --refine, quality mode is --decode-backend wan-vae, prompt enhancement is --enhance-prompt. The Apple Silicon guide covers fast-reload, memory tiers, and troubleshooting.

What's next

  • Image-to-video and longer clips. The 5B is natively image-conditioned; I2V and streaming/causal generation are on the runtime roadmap.
  • MiniMax-H3. The same INT8 QAD machinery now points at H3's 33B omni-modal (video + native audio) teacher. Local audio-video generation is the thing nobody else ships.

We tried to make INT8 fast and closed that door with data. The door we didn't close is the one that matters: bigger, better models, running locally, on the machine already on your desk. That's the direction, and we're just getting started.
